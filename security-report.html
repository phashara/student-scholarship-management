1. Admin เป็นบัญชีเดียว Hardcoded ทั้งระบบ

ระบบทั้งหมดพึ่งพาบัญชี phasharak@gmail.com เพียงบัญชีเดียว ซึ่ง hardcode ไว้ใน 3 จุด:

• firestore.rules — ฟังก์ชัน isAdmin()
• functions/src/index.ts — ฟังก์ชัน requireAdmin()
• src/components/AdminLoginModal.tsx — ค่า AUTHORIZED_ADMIN_EMAIL

// firestore.rules:4-8 function isAdmin() { return request.auth != null && request.auth.token.email_verified == true && request.auth.token.email == 'phasharak@gmail.com'; }

ผลกระทบ: (1) ไม่สามารถเพิ่ม admin หรือกรรมการพิจารณาทุนคนอื่นได้โดยไม่ deploy code ใหม่ (2) หาก Google Account นี้ถูก compromise ระบบทั้งหมดจะถูกเข้าถึง (3) หากเจ้าของบัญชีลาออกหรือเปลี่ยนตำแหน่ง ระบบจะไม่มีผู้ดูแล

แนะนำ: ใช้ Firebase Auth custom claims (admin: true) กำหนด role แทนการ hardcode email — สามารถเพิ่ม/ลบ admin ผ่าน Firebase Console หรือ Cloud Function โดยไม่ต้อง deploy ใหม่ และรองรับหลาย admin ได้
High

2. API ตรวจสอบสถานะ (getApplicationStatus) เปิดเผย PII มากเกินไป

Callable function getApplicationStatus เปิดให้ใครก็ตามที่รู้รหัสนิสิต (8-12 หลัก) ดึงข้อมูลได้:

// functions/src/index.ts:137-148 return { application: { id: doc.id, fullName: data.fullName, // ชื่อ-นามสกุล studentId: data.studentId, // รหัสนิสิต department: data.department, // สาขาวิชา studyYear: data.studyYear, // ชั้นปี academicYear: data.academicYear, status: data.status, // สถานะทุน createdAt: data.createdAt, awardedAmount: data.awardedAmount, // จำนวนเงินที่ได้ } };

Rate limit 60 ครั้ง/นาที ป้องกัน brute-force ได้ระดับหนึ่ง แต่รหัสนิสิตมีรูปแบบคาดเดาได้ง่าย (เลข 8-12 หลัก, ขึ้นต้นด้วยปีที่เข้า เช่น 66xxxxxx) ผู้โจมตีสามารถ enumerate ข้อมูลนิสิตที่สมัครทุนและจำนวนเงินที่ได้รับได้

แนะนำ: (1) ให้นิสิตต้องใส่ทั้ง studentId + submissionToken (UUID) จึงจะดูสถานะได้ (2) ลด response ให้เหลือเฉพาะ status กับ fullName (3) ลด rate limit เหลือ 10-15 ครั้ง/นาที
High

3. ช่องโหว่ PDPA — ไม่มีการจัดการสิทธิ์ข้อมูลส่วนบุคคลตามกฎหมาย

ระบบเก็บข้อมูลส่วนบุคคลที่มีความอ่อนไหวสูง (รายได้ครอบครัว, สถานะหนี้สิน, การเจ็บป่วย, สภาพครอบครัว) ภายใต้ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) แต่ขาดกลไกสำคัญ:

• ไม่มี Privacy Policy หรือแจ้งวัตถุประสงค์การเก็บข้อมูลอย่างชัดเจน
• agreedToTerms ไม่มี link ไปยังเอกสารสิทธิ์ที่ระบุขอบเขตการใช้ข้อมูล
• ไม่มี Data Retention Policy — ข้อมูลเก็บไว้ไม่มีกำหนดลบ
• ไม่มีกลไกให้นิสิตขอดู แก้ไข หรือลบข้อมูลส่วนตัวของตัวเอง (Data Subject Rights)
• public_applications เปิดเผยชื่อ-นามสกุลต่อสาธารณะ

แนะนำ: (1) เพิ่มหน้า Privacy Notice ระบุวัตถุประสงค์, ระยะเวลาเก็บข้อมูล, สิทธิ์ของเจ้าของข้อมูล (2) กำหนด Data Retention Policy เช่น ลบหลังสิ้นสุดปีการศึกษา (3) เพิ่มกลไกให้นิสิตขอลบข้อมูล (4) ทำ Data Protection Impact Assessment (DPIA)

ช่องโหว่ระดับ Medium

4. ไม่มี Firebase App Check

ค่า recaptchaSiteKey ใน config เป็นค่าว่าง แสดงว่ายังไม่ได้เปิดใช้ App Check ผู้โจมตีสามารถใช้ Firebase SDK จากแอปใดก็ได้ (ไม่จำเป็นต้องผ่านเว็บไซต์จริง) เพื่อเรียก Cloud Functions หรืออ่าน public_applications

// firebase-applet-config.json "recaptchaSiteKey": "" // ← ยังไม่ได้ตั้งค่า
แนะนำ: เปิดใช้ Firebase App Check ด้วย reCAPTCHA Enterprise เพื่อยืนยันว่า request มาจากเว็บไซต์จริงเท่านั้น
Medium

5. ข้อมูลอ่อนไหวถูก Cache ใน Browser ของ Admin

เมื่อ admin login ระบบจะ cache ข้อมูลใบสมัครทั้งหมด (รวมรายได้, หนี้สิน, การเจ็บป่วย, ไฟล์แนบ) ลงใน LocalStorage และ IndexedDB ของ browser

// src/services/firebaseService.ts:141-149 if (isAdmin && !snapshot.metadata.fromCache) { try { const filtered = remoteApps.filter(...); safeSetApplicationsLocalStorage(filtered); // ← cache ใน localStorage saveAppsIndexedDB(filtered).catch(() => {}); // ← cache ใน IndexedDB } catch { } }

หากเครื่อง admin ถูกเข้าถึง (คอมพิวเตอร์สาธารณะ, ถูกขโมย, มัลแวร์) ข้อมูลส่วนตัวนิสิตทุกคนจะถูกเปิดเผย ข้อมูลยังคงอยู่แม้จะ logout แล้ว

แนะนำ: (1) ลบ cache ทันทีเมื่อ logout (localStorage.clear() + clearAppsIndexedDB()) (2) ลดขนาด cache — ไม่จำเป็นต้อง cache ข้อมูลอ่อนไหวเช่นรายได้ครอบครัว (3) พิจารณาเข้ารหัสข้อมูลก่อน cache
Medium

6. Admin Operations บางส่วนข้าม Cloud Functions

มี Cloud Functions ที่มี validation ครบ (deleteApplication, clearApplications) แต่ client-side code ยังมีเส้นทางที่เขียน/ลบ Firestore โดยตรง:

// firebaseService.ts — ลบโดยตรงผ่าน deleteDoc() await deleteDoc(ref); // ข้าม callable ที่มี studentId verification // firebaseService.ts — ลบทั้งหมดโดยตรงผ่าน writeBatch const batch = writeBatch(db); snapshot.docs.forEach(item => batch.delete(item.ref)); // firebaseService.ts — แก้ไขข้อมูลโดยตรงผ่าน setDoc merge await setDoc(docRef, cleanData, { merge: true });

Firestore rules ป้องกันไว้แล้ว (ต้องเป็น admin) แต่ callable functions มี safeguard เพิ่ม เช่น studentId verification ก่อนลบ, rate limiting ของ admin operations

แนะนำ: ย้ายทุก write operation ไปใช้ Cloud Functions เท่านั้น เพื่อรวมศูนย์ validation และ audit logging ในที่เดียว
Medium

7. ไม่มี Audit Log

ระบบไม่บันทึก log ว่าใคร (admin/ระบบ) ทำอะไร เมื่อไหร่ เช่น:

• ใครเปลี่ยนสถานะทุนจาก "ยื่นแล้ว" เป็น "ได้รับทุน"
• ใครอนุมัติจำนวนเงินทุน / เปลี่ยนจำนวนเงิน
• ใครลบใบสมัคร
• ใคร export CSV ข้อมูล
• ใครแก้ไข timeline/ประกาศ

หากเกิดข้อพิพาท (เช่น นิสิตร้องเรียนว่าข้อมูลถูกแก้ไข) จะไม่มีหลักฐานตรวจสอบย้อนหลัง

แนะนำ: เพิ่ม audit_logs collection ที่บันทึกทุก write operation ผ่าน Cloud Functions: {action, userId, targetId, before, after, timestamp, ip}
Medium

8. Public Applications เปิดเผยชื่อ-นามสกุลสาธารณะ

Collection public_applications เปิดให้อ่านได้โดยไม่ต้อง login (allow read: if true;) และมีฟิลด์ fullName, department, studyYear — ทำให้ใครก็ตามสามารถดูรายชื่อนิสิตที่สมัครทุนการศึกษาได้ทั้งหมด

// functions/src/index.ts:24-37 — publicProjection { id, fullName: String(app.fullName || '').slice(0, 200), department: String(app.department || '').slice(0, 100), studyYear: String(app.studyYear || '').slice(0, 50), status: ..., finalRank: ..., awardedAmount: ... // เมื่อ status === 'awarded' }

การเปิดเผยว่าใครสมัครทุน (= ต้องการความช่วยเหลือทางการเงิน) อาจถือเป็นข้อมูลอ่อนไหวภายใต้ PDPA

แนะนำ: แสดงเฉพาะ status และ id ในหน้าสาธารณะ ให้นิสิตใช้ submissionToken เพื่อดูข้อมูลของตัวเอง ชื่อ-นามสกุลแสดงเฉพาะในหน้าประกาศผล (เมื่อ status = awarded)

ช่องโหว่ระดับ Low

Low

9. ไม่มี Security Headers (CSP, HSTS)

เว็บไซต์ host บน GitHub Pages ซึ่งไม่รองรับ custom security headers การขาด Content Security Policy (CSP) ทำให้มีความเสี่ยง XSS สูงขึ้น แม้ว่า React จะ escape HTML โดยอัตโนมัติแล้วก็ตาม

แนะนำ: เพิ่ม <meta http-equiv="Content-Security-Policy"> ใน index.html หรือย้ายไป Firebase Hosting ซึ่งรองรับ custom headers ใน firebase.json
Low

10. Self-Healing Timeline อาจเขียนทับข้อมูล

ใน subscribeTimelineConfig มีกลไก auto-fix ที่ตรวจจับ format เก่าและเขียนทับโดยอัตโนมัติ:

// firebaseService.ts:304-306 if (rawStr.includes('28') || rawStr.includes('11.30') || ...) { saveTimelineConfigOnline(data).catch(() => {}); }

เงื่อนไข rawStr.includes('28') กว้างเกินไป — อาจ trigger จาก "28 ตุลาคม" หรือข้อมูลอื่นที่มีเลข 28 ทำให้เกิด write ไม่จำเป็น

แนะนำ: ใช้ version field เท่านั้นในการตัดสินใจ migrate: if (!rawData.version || rawData.version !== data.version)
Low

11. ไม่มี Backup Strategy

ไม่มี automated backup สำหรับ Firestore database หาก admin กด "ล้างข้อมูล" โดยไม่ตั้งใจ หรือ database เกิด corruption ข้อมูลจะหายถาวร — มีเฉพาะ clearApplications callable ที่จำกัด 10,000 documents แต่ไม่มี backup ก่อนลบ

แนะนำ: (1) เปิดใช้ Firestore scheduled backups (2) เพิ่ม confirmation step ก่อนลบข้อมูลจำนวนมาก เช่น ต้องพิมพ์ปีการศึกษา (3) เพิ่ม soft delete (archive) แทนการลบถาวร

สรุป: ระบบมีการปรับปรุงด้านความปลอดภัยไปมากจากเวอร์ชันเดิม — Firestore rules ป้องกันข้อมูลฉบับเต็มแล้ว, Admin ใช้ Firebase Auth แทน hardcoded password, มี Cloud Functions ที่ validate ข้อมูลและจำกัด rate ช่องโหว่ที่เหลือเป็นเรื่อง (1) Single Admin hardcoded email (2) PII exposure ผ่าน status API และ public collection (3) PDPA compliance gaps (4) ขาด audit logging ซึ่งสำคัญอย่างยิ่งหากจะพัฒนาเป็นระบบรับบริจาคทุนที่เกี่ยวข้องกับธุรกรรมการเงิน
